# Rolling flake-update build failures

Start with the named artifact directory rather than rebuilding. Read `head-rev.txt`, `git-status.txt`, and `build.log`; the first lines of `build.log` normally identify each old and candidate input revision. For broad evaluation failures, read through the final `[nix-ci] [ERROR] Evaluation failed:` block and record every `home.<host>` / `system.<host>` label: the alert's `host` is the updater machine, not necessarily an affected configuration, and the short alert tail can omit the target labels. If evaluation itself fails, treat the first concrete assertion or option error as the root; there is no builder to find. A scheduler line that kills one evaluation worker for exceeding its memory budget is not itself fatal when evaluation continues and reaches the build phase. Otherwise enumerate every derivation whose **builder** failed, not final system or Home Manager derivations reporting failed dependencies. Treat later failures as cascade only when their dependency chain leads to an earlier builder failure; one batched build can contain several independent roots, each needing its own ownership and classification. Do not stop at the updater's auto-hold refusal: it reports the first unholdable root or guard outcome, not a complete root-cause inventory. If an input auto-hold rewrites a `follows` edge and then trips the repository's nixpkgs-follows audit, classify that audit failure as a rejected hold/guard cascade rather than a pre-existing config defect; enumerate and diagnose every builder root from the original candidate before deciding whether any local fix exists.

Extract roots structurally instead of grepping every occurrence of `failed`, because build logs contain negative-test fixtures and dependency cascades:

```bash
python3 - "$artifact/build.log" <<'PY'
from pathlib import Path
import re, sys
lines = Path(sys.argv[1]).read_text(errors="replace").splitlines()
for i, line in enumerate(lines):
    match = re.match(r"error: Cannot build '(/nix/store/[^']+\\.drv)'\\.", line)
    if match and i + 1 < len(lines) and "Reason: builder failed" in lines[i + 1]:
        print(match.group(1))
PY
```

Run `nix log <drv>` for every extracted root, even when the retained build log includes a short tail; the auto-hold journal and final system errors are transaction evidence, not substitutes for each builder's own log.

Test ownership in this order:

1. Identify the package/input transition and exact failing build phase or assertion. A version bump may be incidental; compare the package expression and referenced patches at the old input revision, rejected candidate revision, and current upstream tip to find the causal dependency or source change. A group is tested from the transaction state that existed when that group began; later accepted groups may advance another input and change the next retry. Read the accepted lock from current `origin/master` or Forgejo rather than evaluating a stale or operator-dirty primary checkout, then test whether that later input actually removes the earlier root. For an unexpected leaf derivation, inspect `nix derivation show <drv>` for `structuredAttrs.src`, `patches`, and version, then follow `nix-store -q --referrers <drv>` upward until the updated top-level package appears. For evaluation-time package-policy failures where no derivation is available, re-evaluate one labeled failing host with `--show-trace`; the expanded trace often exposes the parent FHS environment or aggregate package and its list index. If policy rejection still prevents package-list inspection, use `NIXPKGS_ALLOW_BROKEN=1 nix eval --impure --json ...home.packages --apply 'ps: map (p: p.name) ps'` only as a read-only provenance probe, never as the proposed mitigation. This proves provenance when the leaf name alone obscures which input introduced it. When a patch fails, inspect both its source commit and the package version receiving it; an unconditional platform guard can wrongly apply a fix written for a newer dependency release.
2. Search nixosconfig for the package symbol and error signature. Inspect every local overlay/override, flake check, package-list inclusion, compatibility comment, package passthru, generated unit, and unit environment/`PATH`/`PYTHONPATH` consumer. When upstream deliberately removes or relocates a symbol, treat a local compatibility supplement that still copies, imports, or exports that retired symbol as **actionable local integration drift**. Fix the whole local contract: gate the supplement and every runtime consumer on the upstream source layout, remove stale invariant imports, and preserve the currently accepted input while allowing the rejected candidate. Test both revisions; a fix that only builds the candidate can break the deployed revision before the lock advances. When an upstream build hook newly forces vendored dependencies to resolve through system libraries, a repository-owned package with `pkg-config` but without the corresponding library in `buildInputs` is **actionable local integration drift**: add the required system library rather than disabling the hook globally. Prove the boundary by diffing the old and candidate hooks and reading the leaf builder log for the exact missing `.pc` file. A documented local hardware or ABI requirement is not enforced if the configuration still consumes a moving upstream default alias. When that alias advances across an incompatible major version, classify the failure as **actionable local integration drift** and encode the required major package set explicitly; this is a compatibility boundary, not a temporary input pin. Treat removed or scope-split upstream configuration defaults the same way: if a local guard, unit, or repository check reads an implicit default, inspect the upstream change and move the value into the correct owned scope (for example rootful versus rootless) rather than restoring a shared default that upstream deliberately removed. Update both the runtime consumer and its invariant check so the check cannot keep evaluating the retired path. Apply the same ownership test to capability-selection semantics: when an upstream input fixes an alias or fallback so an explicit selector becomes a real allowlist, a local config that depended on the accidental fallback is actionable integration drift. Diff the resolver at the old and rejected revisions, then explicitly list every locally required capability and run the repository-owned assertion against the exact rejected input. For service startup or execution failures, inspect the generated unit and its `PATH`; for a package/check builder assertion about resolved capabilities, do not invent a service-`PATH` explanation.
3. Re-evaluate against the exact rejected input without changing `flake.lock`. Do not assume `head-rev.txt` names a Git object retained by the primary checkout: rolling transactions can use temporary commits. Prefer the immutable repository and input source paths printed in the retained log; otherwise reconstruct from the committed source plus `--override-input`. When the failure occurred during repository checks or broad host evaluation, run the same breadth first so a successful unrelated-host evaluation cannot clear failures in other configurations:
   ```bash
   nix flake check --no-build \
     --override-input <input> <candidate-flake-url>
   ```
   Then dry-evaluate each directly affected host:
   ```bash
   nix build --dry-run --no-link \
     --override-input <input> <candidate-flake-url> \
     .#nixosConfigurations.<host>.config.system.build.toplevel
   ```
   Require successful evaluation and inspect the planned derivation names to confirm the intended dependency major/version. These commands prove evaluation, repository-owned assertions, and the dependency plan only; do not describe them as completed builds. For a local leaf package or OCI image, build that exact output against the rejected input before running the host dry-build; this gives completed build/test evidence without waiting for unrelated known-broken roots in the full closure. When smoke-testing imports from a candidate package, clear inherited Python injection (`env -u PYTHONPATH -u PYTHONHOME <candidate-python> ...`): the investigator's running gateway environment can otherwise supply modules from the deployed revision and create a false pass or an irrelevant mixed-version failure. Enumerate real configuration keys with `nix flake show --json` instead of inferring a flake attribute from the final derivation name, because those names can differ. For systemd environment or command changes, build the generated unit for both the accepted and rejected inputs, inspect the rendered directives, and run `systemd-analyze verify` on the actual unit file. A Nix unit attribute can realize to a directory containing `<name>.service`; detect that shape and verify the inner file rather than passing the output directory to systemd. If the updated input is itself a flake whose `nixpkgs` follows the consumer, also dry-evaluate its package twice: once with its own lock and once with `--override-input nixpkgs <consumer-candidate>`. A package that evaluates with its own lock but injects a version-specific patch that fails against a supported followed input is an **upstream packaging compatibility bug**, not evidence that the consumer should drop `follows` or add a nightly pin. Call it actionable only when nixosconfig documents and owns the dependency boundary.
4. Confirm transaction semantics from the updater journal: whether the failed group was reverted, which independent groups were committed, and whether push-deploy activated only the accepted lock state. Report runtime health separately from the rejected candidate build. Resolve each runtime unit's manager scope before probing it; Hermes gateway and other Home Manager services require `systemctl --user`, while the updater itself is a system unit. An inactive same-named system unit does not prove that an active user service is unhealthy.
5. Diagnose every `push-deploy` timeout independently of the rejected build. From the sender journal identify the target and staged closure, confirm the guest is running, then inspect `systemctl status push-activate.service`, `systemctl list-jobs`, and journals of running/waiting units on the target. A fast Home Manager success does not prove activation completed: `switch-to-configuration` can remain blocked on `multi-user.target` while a required service restart-loops. Follow the first failing unit to its own causal error. If a `podman-ts-<share>` unit reports `nodeKeyExpired`, `NeedsLogin`, or rejected credentials, use the Tailscale-share recipe in `service-failure-recipes.md` and classify enrolment as external rather than inventing a deployment/config fix.
6. Search upstream issues/PRs using the package name plus the distinctive error. Check PR merge state, not merely open/closed state, and compare the merge commit's ancestry or timing with the rejected revision: a fix merged after the candidate remains an upstream candidate failure and normally needs only the next rolling retry. Check every independent root separately; one candidate can predate several unrelated merged fixes. If the same unmodified upstream package expression remains broken at current tip and nixosconfig only consumes `pkgs.<name>` **without a local compatibility requirement**, classify it as **upstream**. Do not add a local pin or overlay merely to make a nightly bump pass while the installed version and hosts remain healthy. For stale package holds, reproduce with the same package-policy settings as the updater (for example unfree allowance) before interpreting the result; otherwise an earlier policy rejection can mask the current one. If current upstream still fails because a bundled dependency is now marked insecure or end-of-life, report the security disposition explicitly and leave removal versus continued hold for operator review—never auto-permit the insecure package merely to clear the hold warning. For `linux-*-modules` aggregation failures, inspect the exact external-module input derivations before blaming the kernel or local host selection. A missing signing sidecar such as `<module>.ko.cer` can be an upstream packaging-contract regression in one external module even though the failing derivation is the aggregate kernel module tree; search upstream by the missing filename and module package, then verify whether its packaging fix landed after the rejected candidate.
7. For dependency-fetch or release-discovery failures, rerun the exact URL and parser before changing configuration. Preserve the fetched page in scratch, run the updater's exact extraction pipeline, and compare the discovered release with the configured package. If the same parser now returns the already-installed latest release, classify the earlier empty response as transient vendor-page delivery and do not rewrite a working parser from one failed fetch. If the parser fails reproducibly, inspect the response structure and page source for a vendor-published structured feed before changing selectors: a site can retain release data in JSON while removing the static HTML elements the updater scraped. Prefer the vendor's documented/current JSON feed over rendered-page parsing; filter the exact supported series, stability flag, edition, platform, and architecture, then require the selected archive URL to match the package's protected URL shape before preserving the existing checksum and archive-layout verification. Add fixture cases for series boundaries, prereleases, and wrong-platform URLs, replay the new parser against the live feed using a scratch package copy, and classify this deterministic parser-contract drift as **actionable**. For actual fetch failures, test DNS and routing before blaming the package. Compare the fleet resolver with a public resolver, inspect the selected address, and retry with an explicit address family when the connection times out. Matching public/fleet DNS plus a repeatable direct timeout supports an external path or origin failure; a fleet answer of `0.0.0.0` plus an unrelated local virtual-host certificate proves a local DNS sinkhole and is **actionable** local infrastructure. Use pfSense MCP only after loading its skill and only when evidence requires excluding explicit host/domain overrides; recommend a reviewed DNSBL allowlist and retry, not a nixosconfig PR unless the blocking policy is demonstrably owned there. Treat an updater auto-hold refusal for an auxiliary derivation as transaction disposition, not root cause, and do not let the auto-hold candidate hide other independent builder failures in the same batched build.

Use these operational labels:

- **upstream** — the rejected input contains an upstream package/dependency bug; no nixosconfig PR unless a local mitigation is explicitly warranted.
- **actionable** — nixosconfig owns the fault or the running system needs a local change; use the config-issue PR workflow when appropriate.
- **transient** — the same candidate succeeds on a clean retry or evidence points to temporary resource/network failure rather than deterministic source state.
