# Service-failure investigation recipes

Load this reference only when the alert matches one of these failure shapes.
All probes remain read-only.

## systemd sandbox/namespace failure

1. Read the unit journal from before its first failed start and inspect the generated unit with `systemctl cat <unit>`. Look for earlier `Failed to parse BindPaths=` or `RequiresMountsFor= path is not absolute` messages; a later `Failed to set up mount namespacing: <destination>: No such file or directory` can be a downstream symptom of an ignored source bind, not proof that the host destination vanished.
2. Check every bind source and destination on the host with `stat`/`findmnt`, then inspect `TemporaryFileSystem=`, `BindPaths=`, `BindReadOnlyPaths=`, and `RequiresMountsFor=` together. With `TemporaryFileSystem=/mnt`, destination directories are created inside the private namespace only after the bind definition parses correctly.
3. For space-bearing systemd path lists, use `\\x20` in the generated unit value (for example an indented Nix string containing `\\x20`). Do not use backslash-space: systemd splits the directive on whitespace first and treats the pieces as malformed entries. Remove redundant space-bearing `RequiresMountsFor=` paths when an explicit mount-unit dependency already supplies the ordering.
4. Reproduce parser behavior with a minimal scratch unit when escaping is uncertain, but verify the actual generated NixOS unit before proposing a fix. Build the unit derivation, inspect its exact directive, run `systemd-analyze verify`, and require a successful `nixos-rebuild dry-build --flake .#<host>`; a Nix parse or evaluated list does not test systemd tokenization.
5. Search sibling service modules and documentation for the same escaping pattern. Fix all confirmed instances of the same invariant in one focused PR, while leaving unrelated sandbox refactors out.

## Timer-driven oneshot failure

1. Read `systemctl status <unit>`, the unit journal for the alert window, and the timer's `LastTriggerUSec` and next trigger. Do not infer success from a payload built with `journalctl -n N`: a noisy prior successful run can fill the tail and hide the current invocation's final error.
2. For `Result=timeout`, inspect the full invocation from start through systemd's termination and compare the last progress marker, completed-item count, and observed cadence with the configured timeout. Classify a steadily progressing job killed exactly at `TimeoutStartSec` as an undersized config budget, not a hung process or upstream outage; expected per-item outcomes remain expected even though the overall invocation failed.
3. Fix an undersized timeout at the narrowest workload boundary. When one shared service constructor covers both a short current job and a long exhaustive/backfill job, give only the long mode additional headroom, retain a finite bound, and add evaluated assertions for both budgets so the routine path is not silently weakened.
4. When a failed assertion embeds a command substitution such as `test "$(command)" = <expected>`, treat the failure as proof only that the actual value differed. Search preceding output, saved headers, and retained artifacts for the actual value; if an ephemeral VM or scratch tree is already gone and the value was never logged, report it as unknown rather than inferring a likely status or exception.
5. For candidate lock/package updates, compare the versions of the directly implicated package and its relevant runtime/authentication dependencies between the accepted and candidate revisions before blaming upstream. Unchanged versions weaken a package-regression diagnosis and support an isolated fixture/test classification only when the remaining gates, receipts, and recent runs also support it; version equality alone is not proof of transience.
6. Correlate the oneshot's start/error timestamps with the dependency's `ActiveExitTimestamp`, `ActiveEnterTimestamp`, and unit journal. Inspect the auto-upgrade/deploy unit when the dependency restarted in the same window. Probe the dependency's direct backend and public health endpoints after the event to separate a brief restart race from a continuing outage.
7. For exit 143, `Terminated`, an invalid monitor/resource receipt, or a missing final transaction disposition, inspect PID 1's journal around the exact termination for `switch-to-configuration`. `Restart=no` does not exonerate activation: NixOS can stop a changed active unit and start its replacement as part of the switch, producing an immediate rerun without a systemd restart policy.
8. Inspect the NixOS service's evaluated `restartIfChanged` and `stopIfChanged` values, not only the generated unit. For a long-running timer transaction whose next invocation can safely consume the new definition, set both false so activation cannot SIGTERM an in-flight run; apply the same invariant to sibling candidate/canary units with identical lifecycle semantics and assert the evaluated values.
9. Keep interruption and payload verdict separate. Report any test or build failure observed before termination as additional evidence, but do not call the candidate accepted, rejected, or reverted when the runner explicitly lacked a final disposition. The activation-policy fix must preserve the transaction long enough to report its real verdict, not suppress the underlying failure.
10. Classify a dependency restart overlap as transient only when the dependency restart falls inside the oneshot invocation, current health has recovered, recent prior runs succeeded, and a future timer retry is scheduled. Classify activation terminating the monitored oneshot itself as a config issue when the unit should survive switches; do not reduce it to a transient merely because activation automatically reran it.
11. Before running a host dry-build for the fix, check whether activation has already restarted the same production-depth job. Do not overlap costly jobs; use parse, formatting, and evaluated-policy checks immediately, and state plainly when the full dry-build is deferred rather than competing for the host.
12. Prefer `journalctl -u <unit>` or `_SYSTEMD_UNIT=<unit>` over host-wide grep. Aggregators such as Loki can log query strings containing the service name, recursively flooding broad searches and obscuring causal lines.

## Boot-time crash-notifier failure during activation

1. When `switch-to-configuration` reaches activation and then reports `warning: the following units failed`, treat the named unit as the immediate upgrade root rather than blaming the candidate commit or nixpkgs. Verify `/run/current-system` and `configurationRevision` separately: activation can install the target successfully while returning non-zero because a wanted oneshot failed.
2. Read the notifier's status, journal, generated unit, and generated executable. If the journal contains only an exit status, inspect the shell's control flow around commands that can fail silently; `writeShellApplication` adds `set -e`, so a failed command substitution such as `value=$(grep ...)` terminates the script even when an empty value is a valid result.
3. Inspect the notification ledger and artifact tree read-only before reproducing. For systemd-pstore, enumerate every `<crash-id>/<record-number>/dmesg.txt`; record numbers are not fixed at `001`, and one panic may span several numbered records. Re-measure which crash IDs are absent from the ledger so old retained records are not mistaken for the triggering input.
4. Do not start or trace the production notifier during RCA: it can update its ledger and send duplicate pages. Reproduce only the parsing helper against read-only artifacts or a scratch fixture, preserving the service's shell options.
5. Fix the data-layout invariant rather than special-casing one record number: pass a glob such as `"$pstore/$id"/*/dmesg.txt`, use `grep -h` when multiple files may match, and explicitly tolerate no optional fault marker with `|| true`. Apply the same non-fatal rule to every optional summary extraction in that notifier, because an artifact can be valid without matching the preferred marker set.
6. Verify the source with `nix-instantiate --parse`, run the affected host dry-build, realize the notifier derivation so `writeShellApplication` runs its shell checks, inspect the generated executable for the rendered glob and error handling, and run a read-only fixture against both a non-`001` record and a file with no marker. Never describe a dry-build plan as a completed system build.

## Kernel panic with missing kdump

1. Reconstruct the crash from all independent channels before assigning ownership: the guest's pstore tree, the hypervisor-owned serial log, host-side recovery artifacts, and hypervisor VM stop/start journal. Align guest uptime with wall-clock lifecycle events; a later manual power cycle can make firmware output look like an automatic panic reboot.
2. Separate the terminal fault mechanism from the first corruptor. For an instruction-fetch page fault at a suspicious kernel address, compare the RIP's low bits with `System.map`/`vmlinux` and apply the printed kernel KASLR offset. A jump to an unrelocated or incorrectly relocated exception entry proves corrupted control/vector state, but a destroyed stack or double-fault trace does not identify the subsystem that first corrupted it.
3. Compare distinctive normalized signatures across retained captures: CPU idle task, exception-entry low bits, stack-overflow/double-fault shape, kernel versions, and preceding resource telemetry. Treat a recurring signature as one corruption class while preserving uncertainty about whether the owner is guest kernel, hypervisor, or hardware.
4. Prove the kdump failure independently: check that the crashed kernel reported `Kdump: loaded`, verify the current host's `kexec_crash_loaded`, and inspect serial output after the terminal panic. A direct transition from panic to firmware with no capture-kernel boot text and no vmcore artifacts means the capture kernel never took control; do not call this a dump-writer failure.
5. Inspect `crash_kexec_post_notifiers` and every panic-notifier/kmsg-dumper frame that ran before the expected handoff. The option deliberately delays kexec and increases failure risk because notifiers execute in already-corrupted state. When serial or netconsole independently preserves panic text, prefer early kexec over post-notifier diagnostics; remove the delaying option only when the trace shows that pre-kexec notifier work is the local capture defect, not as a speculative response to every missing dump.
6. Track source, deployed closure, and booted kernel as three distinct states. Verify the signed fix is an ancestor of the deployed `configurationRevision`, compare `/run/current-system/kernel-params` with `/proc/cmdline`, and state explicitly when a kernel-parameter fix is landed and deployed but still awaits reboot. Do not open a duplicate PR or claim the fix is active merely because userspace switched successfully.
7. Report the incident in two layers: the best-supported crash classification and the independent capture-path classification/action. Do not overstate a capture fix as fixing the underlying kernel corruption.

## Alloy log-shipper startup/config failure

1. Resolve the deployed unit name from nixosconfig or generated units before probing it. Do not trust an alert description that says only `alloy`: service names often remain stale after a module rename. If the named unit is absent, narrowly list matching services and processes to find the real unit before drawing conclusions.
2. Read status and journal from the activation boundary, inspect `systemctl cat <unit>`, and collect `ActiveState`, `SubState`, `Result`, `NRestarts`, and `ExecMainStatus`. A Loki silence query cannot contain a shipper's local startup error once that shipper has stopped, so the host journal is authoritative for restart loops.
3. When Alloy reports `expected block label to be a valid identifier`, inspect the rendered block at the reported line and trace the label back to its Nix option. Prometheus job names and other user-facing labels may allow hyphens while Alloy component labels do not. Make the internal label match `[A-Za-z_][A-Za-z0-9_]*` and add an evaluation-time assertion (or separate internal identifier option) so a future invalid label fails before activation; do not rely on a runtime restart loop to validate generated HCL.
4. When Alloy rejects `loki.write.wal` because the experimental stability level is disabled, treat it as a package/config compatibility regression. If WAL durability is intentional, preserve it and opt in explicitly at the Alloy process boundary; do not delete WAL merely to make startup succeed.
5. Confirm the exact CLI flags against the deployed binary with `alloy run --help`. For any generated-HCL fix, parse the Nix file, dry-build the affected host, build and inspect the generated systemd unit and HCL, run `systemd-analyze verify` on the unit, and validate the generated config with the same Alloy binary and stability flags. This checks Nix rendering, component references, CLI spelling, and Alloy's parser rather than assuming evaluation or a one-line source edit is sufficient.
6. Check whether the unit comes from a fleet-shared module and whether the same package revision reached sibling hosts. One host's silence alert may be only the first visible symptom of a shared restart-loop regression; keep the code fix at the shared invariant while reporting only runtime states actually verified.

## .NET named-mutex startup failure

1. When an HTTP backend in a VM or container times out while its parent supervisor remains active, inspect the guest's serial/journal output and probe the backend directly. An active VM process proves only that the guest booted; a daemon can exit during application initialization while the parent unit stays healthy.
2. For `I/O exception attempting to acquire ... singleton mutex` or `The system cannot open the device or file specified`, correlate the first failed start with the deployment timeline and compare the **runtime** version printed by the application before and after the update. Do not stop at the application package version or output path: a framework-dependent application can remain byte-identical while its .NET runtime changes underneath it.
3. On recent .NET servicing releases, named mutexes use a user-scoped directory below `XDG_RUNTIME_DIR` and fall back to `HOME`. Inspect the generated unit for both variables and the system user's home; a hardened user with no writable home and no runtime directory will fail every restart, so retries are evidence of persistence rather than recovery.
4. Fix the service boundary by declaring a private systemd `RuntimeDirectory` with restrictive mode and setting `XDG_RUNTIME_DIR` to that path. Preserve the unprivileged user and sandbox; do not pin the runtime, make the home writable, or weaken filesystem protections merely to restore mutex creation.
5. Parse the Nix source, dry-build the affected host, build and inspect the generated unit for the exact environment and runtime-directory directives, then run `systemd-analyze verify`. Also inspect declarative health-check failure actions before attributing an observed restart to an operator or the RCA agent.

## Cratedigger live-world integrity failure

1. Separate the candidate transaction from the post-run audit. Read the service properties and journal around `ExecMain` and `ExecStopPost`: if candidate gates completed, the lock was published, and only `cratedigger-daily-live-world-audit` failed, report the candidate as accepted/published and investigate the audit as a distinct production-integrity finding. Do not describe the candidate as rejected merely because the systemd unit is red.
2. Run the deployed strict audit read-only on doc2 with `sudo /run/current-system/sw/bin/cratedigger-live-world-audit`. Parse `groups.a.members`, `groups.b.members`, and `groups.c.members`; the report deliberately has no flat `violations` list, so looking only for that key can hide the exact member while aggregate counts remain nonzero. Use the tracked audit only for cohort/new/changed classification because it intentionally emits aggregates across the daily SSH boundary.
3. For `denylist_without_authority`, inspect the named request, its replacement lineage, the exact `source_denylist` row, and `download_log` rows on both source and successor. Use `pipeline-cli show <request_id>` plus read-only `pipeline-cli query ... --json`; match timestamps, username, reason, and source decision rather than assuming a row is intrinsically invalid. A direct `pipeline-cli` process does not inherit the audit wrapper's database credential: run it in a privileged remote shell that reproduces the deployed wrapper without printing the secret, for example `password="$(grep -m1 '^PGPASSWORD=' /run/secrets/cratedigger-pgpass | cut -d= -f2-)"; test -n "$password"; export PGPASSWORD="$password"; pipeline-cli show "$id"`. When embedding this in SSH, quote the outer command so `$password` and `$id` expand on doc2, not doc1. Capture verbose `show` output into local scratch and extract the status, denylist, and relevant download-history sections instead of flooding the RCA context.
4. Specifically test whether a replacement/adoption operation reassigned the rejecting `download_log` row to a successor while leaving its `source_denylist` row on the replaced request. That split removes the audit's decision authority even though the original rejection was valid. Verify that the local remote-tracking ref is current before inspecting source: compare `git ls-remote <remote> refs/heads/main` with `git rev-parse origin/main`, fetch `origin main` when they differ, then use `git show origin/main:<path>`. Never treat a stale `origin/main` as current merely because `git show` succeeds; fetching updates the remote ref without switching or editing the shared checkout.
5. For a repeat alert naming the same audit member, use the prior RCA as the hypothesis and run only four current checks: the candidate verdict in the exact invocation journal, the strict audit member, the tracked cohort classification, and `pipeline-cli show` for the source and successor. Filter the full exact-invocation journal for transaction and audit verdict lines rather than returning an unbounded fuzz transcript; do not use a small `journalctl -n` tail, which can omit the candidate disposition. Inspect freshly fetched remote source separately from production data: a newer source fix does not repair an already orphaned row, while unchanged source plus unchanged rows means the prior application fix and manual data-repair disposition still stands. Report measured persistence instead of reopening discovery.
6. Classify a proven application mutation/provenance defect as **actionable**, not a nixosconfig config issue. State the source invariant that must be fixed and that production data needs manual repair, but do not mutate either during RCA and do not open a nixosconfig PR for an application-owned bug. Report current successor/runtime health separately so the integrity alarm is not mistaken for an outage.

## HTTP 404

1. Fetch public response headers and a short body fingerprint; a page from a different service is stronger evidence than the status code alone.
2. Probe the loopback backend directly both with its internal nginx `Host` and with an unmatched/default host, for example: `curl -sS -o /dev/null -w '%{http_code}\n' -H 'Host: <internal-vhost>' http://127.0.0.1:<port>/<path>`.
3. Inspect generated nginx configuration and search nixosconfig for every claimant of that loopback port. If the internal Host succeeds while the public request reaches another vhost, classify it as a duplicate backend socket/Host-routing config issue, not a missing file.
4. Confirm the source file exists and compare a known-good sibling endpoint. Shared nginx can be healthy while one public hostname is routed to the first vhost on a colliding socket.

## HTTP 421 on a tailnet URL

1. Resolve the URL and identify the exact Tailscale peer; confirm that peer is online rather than assuming the origin host or alert bridge owns the URL.
2. Fingerprint the response and probe several times. Search declarative sidecar/proxy configuration and DNS ownership for an SNI/Host or stale-record discrepancy.
3. If repeated current probes succeed and there is no configuration discrepancy or supporting service-log failure, classify the 421 as a transient external proxy response. Do not create a speculative config fix or conflate it with an unrelated config failure in the same batch.

## Tailnet timeout to a dedicated share peer

1. Match resolved A/AAAA addresses to `tailscale status --json`, then inspect the peer's `Online`, `Expired`, `KeyExpiry`, and `LastSeen` fields. Confirm with `tailscale ping`; `peer's node key has expired` is stronger evidence than a generic HTTP timeout.
2. On the hosting machine, read the `podman-ts-<share>.service` journal for `nodeKeyExpired`, `NeedsLogin`, or auth-key rejection. Probe the application backend directly: a healthy local API plus an expired/offline share peer isolates the failure to Tailscale enrolment.
3. Treat a retired or invalid auth key after node-key expiry as external control-plane/enrolment state requiring manual re-enrolment unless nixosconfig contains a demonstrably wrong secret reference, hostname, tag, or lifecycle policy. Do not call a running container healthy when containerboot is restart-looping through `NeedsLogin`.
4. Give the existing generated recovery command, normally `sudo tailscale-share-login <name>`, and the durable admin action: disable key expiry for the correctly tagged service node. Do not open a PR for a healthy local service whose only fault is expired control-plane identity state.

## Push monitor: `No heartbeat in the time window`

1. Separate the real probe verdict from heartbeat delivery. In the probe journal, identify command timeouts/non-zero exits, successful payload checks, missing URL files, and explicit heartbeat-push failures; a healthy probe message alone does not prove Kuma accepted the push.
2. Compare successful probe completion timestamps with Kuma's pending/retry/DOWN timestamps. Inspect the generated runner to confirm when it pushes relative to command completion, then inspect declarative probe cadence and `intervalSecs`.
3. Require deadline headroom: `intervalSecs` must be comfortably larger than systemd probe cadence, normally 25–50%. Equal values can place a healthy push on Kuma's evaluation boundary; one missed probe can then become a false DOWN page despite later healthy checks. Fix the declarative deadline rather than masking the real probe.
4. Classify an isolated command timeout as transient only when deadline headroom is adequate and later accepted heartbeats clear Kuma. Classify equal cadence or a stale push destination as a config issue while reporting runtime service health separately.
5. Before opening a deadline fix, search every sibling deep probe for the same equal-cadence configuration and inspect recent analogous fixes. Correct all confirmed instances of the shared invariant in one focused PR when they have the same semantics; otherwise serial alerts will expose the same boundary race one service at a time.
